# TTS deployment validation checklist

Use this checklist to validate a new remote deployment or continue a paused
CPU-to-GPU migration. It contains no live infrastructure status. Keep your
instance identifiers, operational notes, credentials and billing information in
local files outside version control. Start with [README.md](README.md) for
runtime preparation and connection setup.

## Before starting

1. Set `PROJECT_ID`, `ZONE` and `INSTANCE` to your own deployment values. Check
   the existing instance state and disk before provisioning a replacement.
2. Review your budget and automatic stop policy. Persistent disks and images
   can incur charges while compute is stopped. Do not use an unattended retry
   loop to repeatedly start billable instances.
3. Preserve a backup of the CPU configuration and a verified copy of the model,
   references and training data. Do not remove the only verified copy.
4. Keep the API bound to `127.0.0.1:9880`, accessed through authenticated SSH.
   Use a separate tunnel port such as `19881` for testing alongside an existing
   desktop connection; match the test client's `gptSovits.baseUrl` to that port.

## Server validation

1. Start the chosen instance explicitly, register its SSH host key through
   `gcloud compute ssh`, and set `CLOSURE_TTS_PROJECT`, `CLOSURE_TTS_ZONE` and
   `CLOSURE_TTS_INSTANCE` for the tunnel.
2. Check `/closure/health` through the test tunnel. For GPU inference, confirm
   CUDA is available, FP16 is enabled and the intended GPU is reported.
3. Upload the latest adapter, protocol and cache files. Run the appropriate
   installer's `--check-only` mode before enabling the service. Verify all
   original models and references against your transfer manifest, allowing
   only regenerated bytecode where applicable.
4. Stop the TTS service while running `verify-reference-cache.py` in the
   selected environment as the service user. Compare each reference miss
   against an upstream miss, and each cache hit against an upstream warmed
   hit; reference extraction consumes Torch RNG. Save the six waveform
   comparisons locally, then restart the service.
5. Verify systemd startup after a real guest reboot. Model loading and prewarm
   time are separate from per-request synthesis latency.

## Desktop validation

1. Run `benchmark-stream.py` through the tunnel. Record the first complete WAV,
   total synthesis and audio duration for short and multi-fragment replies.
2. Compile and run `RemoteStreamingSmoke.java --play` using the application's
   Java dependencies. Measure the first native JavaFX `PLAYING` event as well
   as audio availability. Verify fragment order, intelligibility and the
   absence of audible gaps on a longer reply.
3. Exercise cancellation, timeouts, error frames and temporary WAV cleanup.
   Run `RemoteClientSmoke.java` with its managed-tunnel option to verify that
   the tunnel starts and closes with the application.
4. Only after server and native playback checks pass, activate the desired
   local voice configuration and set `gptSovits.streaming=true` when using the
   framed endpoint. Check environment overrides and restart Closure.
5. Retain the CPU fallback and recovery copy until data integrity, desktop
   playback and reboot checks pass. Stop unused compute explicitly and close
   temporary tunnels after testing.

## Historical validation coverage

The recorded development checks included 53 focused Java tests covering early
fragment delivery, playback order, cancellation, stream errors and truncation,
whole-stream timeouts, remote reference paths and temporary WAV cleanup. CPU
cache verification passed all six miss/hit comparisons with identical PCM.

Historical L4 timings and CPU diagnostics are summarized in
[latency-report.md](latency-report.md). They do not certify a later deployment:
controlled GPU cache comparisons and actual native playback timing must still
be measured on the environment being released.
