# Closure 人物风格与对话评测

这套设计用于比较角色表达、上下文组织和模型后端。每组评测固定角色卡、文本提示词与测试条件，按案例要求核对模型回复和应用会话行为。

## 角色卡与证据

角色卡概括可露希尔的身份、性格和与用户相处的方式。随应用发布的文本提示词规定如何组织回复、判断现实信息和填充 JSON。两份资源共同构成请求的系统指令。 [角色卡](../closure-role-card.zh-CN.txt) · [文本提示词](../../../src/main/resources/prompts/closure-system-prompt.txt)

语音依据为 [PRTS 语音记录](https://prts.wiki/w/%E5%8F%AF%E9%9C%B2%E5%B8%8C%E5%B0%94/%E8%AF%AD%E9%9F%B3%E8%AE%B0%E5%BD%95)。[场景索引](source-scenes.json)保留 38 项元数据与本次读取的 HTML 校验值，原文和音频以来源页为准。V01 至 V38 是本设计的索引，实际语音编号另存为 `source_voice_index`，两者不能互换用于音频配对。页面修订号也不保证冻结所有转入模板，因此同时保留读取时间和校验值。

以下解释属于对台词的归纳，引用指向对应场景，而非新增的标准回复。

| 归纳 | 场景索引 |
| --- | --- |
| 技术自信，抱怨忙碌时仍会承担责任。 | V01、V06、V16、V38 |
| 以熟悉的调侃和具体举动表达关心。 | V07、V09、V33、V36 |
| 表达可自我修正，长短随场景变化。 | V04、V13、V14、V32 |
| 商业玩笑取决于语境。 | V02、V10、V23、V37 |

按桌宠用途分组，人物与互动场景 21 项，战术与行动场景 16 项，标题 1 项。这是工作分类。晋升、节日、战斗等条件应随引用保留；游戏背景不会自动成为用户的现实经历或双方的聊天记忆。

## 两条评测轨道

[案例集](cases.v1.json)有 40 例，每类 5 例。30 例检查模型对固定输入的回应；10 例检查应用服务如何维护会话与记忆。所有用户、项目、日期、消息和记忆夹具均为合成数据。

| 类别 | 数量 | 轨道 | 重点 |
| --- | ---: | --- | --- |
| A 日常分享与意图 | 5 | 模型 | 接话、主题选择、尊重输出形式 |
| B 求助与能力边界 | 5 | 模型 | 回答具体问题、如实表达不确定性 |
| C 关系与情绪回应 | 5 | 模型 | 熟悉感、适当关心、语境变化 |
| D 多轮理解与表达稳定 | 5 | 模型 | 指代、更正、承接和跨轮复读 |
| E 长期记忆行为 | 5 | 应用集成 | 写入、更正、过期、删除和项目作用域 |
| F 事实与引用边界 | 5 | 模型 | 世界观、现实事实、记忆来源和新鲜度 |
| G 朗读文本与语气 | 5 | 模型 | 语义一致、可朗读性和情绪意图 |
| H 会话生命周期 | 5 | 应用集成 | 关闭重开、失败、取消、并发和换模型 |

模型轨道中的历史、摘要和长期记忆都由测试驱动器预先提供。通过这些案例只能说明模型会使用给定上下文，不能据此认定应用已经实现持久记忆。应用集成轨道需要真实的会话和记忆服务；缺少能力时记录 `UNSUPPORTED`，不能计为通过。

案例没有固定的角色回答答案。少数中性助手前文用于测试指代；F02 特意包含一句助手开场猜测，检查它是否被误当成用户事实；G03 的额外回复夹具用于检查后处理。它们均为合成数据，不作为人物示范或生成目标。

## 输入与输出约定

生成请求使用所测版本的角色卡与文本提示词，以及 `generation_input` 和当前案例步骤实际返回的应用结果。驱动器必须按字段白名单组装请求。`checks`、`state_oracle`、评审规则、证据索引和后处理夹具都只供评审使用，不能发送给生成模型。

输入先采用 `generation_input_defaults`，再应用案例字段：运行环境按字段合并，其余字段整体替换。集成案例中的声明只用于初始化测试存储；后续每轮必须从真实测试服务读取当前会话、摘要和记忆。驱动步骤、存储种子和状态预言不会整体注入生成请求，服务成功结果也不能由预期值伪造。

历史通常按用户和助手的完整轮次回放，F02 的合成开场是专门声明的例外。历史助手回复只回放 `displayText` 正文一次，本轮输出仍须遵守 JSON 协议。`displayText` 与 `speechText` 是同一个回复的两个字段，不是两轮对话。`user_turns` 中的每条输入分别执行一次；收到并提交上一条有效回复后，再组装下一次请求。

每次返回一个 JSON 对象，含 `displayText`、`speechText`、`dominantEmotion`。显示文本承担完整回答，朗读文本保留中心语义和重要数字，允许概括代码与长路径。朗读长度沿用 120 字符上限；20 至 80 字符是常规目标，不强迫所有回答填到固定长度。

情绪按整条回复的主意图选择，沿用现有五个标签。疑问标点不自动决定语气。G03 单独检查带疑问的调侃，模型原始标签和应用最终标签分别记录。现有解析器对混合线索的中性回退需要在接入阶段核对，不能把应用改写标签造成的差异记成模型失误。

## 比较方式与评分

分开保留三种结果，不能混成一张模型排名：

1. 现用系统基线：保持已部署提示词与单轮行为，记录当前端到端表现。
2. 上下文方案比较：同一个模型分别使用旧组织方式和角色卡加统一历史夹具，衡量提示词与上下文改造。
3. 模型比较：各模型使用相同的角色卡、输入、历史、摘要和记忆夹具，衡量模型差异。

首轮建议以现用 `gpt-6.1-sol` 为对照，再评估 `qwen4-max` 与 `deepseek-flash`。这些是待测候选，不代表已具备账户权限或已评出优劣。候选公开资料见 [OpenAI](https://developers.openai.com/api/docs/models/gpt-6.1-sol)、[千问](https://help.aliyun.com/zh/model-studio/qwen4-max)、[DeepSeek](https://api-docs.deepseek.com/)。

每个模型固定一套受支持的对话参数，并记录实际发出的推理、采样和结构化输出选项。当前 Sol 路径没有发送请求中的 `temperature`；跨供应商评测不能假设同一个数值在所有模型上都生效。模型可用性、调用总数和费用上限在执行前确定。30 个模型案例每次完整执行至少需要 45 次生成，D05 本身有 16 轮；重复采样和重试另计。

第二组比较首先衡量提示词与上下文的联合改造。若要分别归因，再补做旧／新提示词与无／有统一历史的四组对照，不能从联合改造的结果直接断言哪个因素起效。

先隐藏模型名称，对模型轨道按 1 至 5 分评审：回答问题 35%、人物表现 25%、自然程度 25%、朗读文本 15%。这些权重是首版设计参数。人物表现看反应方式与态度，不按是否出现某个角色词汇加分。固定句式的频率单独记录，并结合上下文人工判断，不把重复一个常见词直接判失败。

JSON 协议不合法、虚构用户事实、声称完成未成功的操作，以及违反明确偏好等，属于对应案例的阻断问题。应用集成案例按状态与副作用判定，不与模型风格分数平均。结果使用 `PASS`、`FAIL`、`UNSUPPORTED`、`ERROR`、`NOT_RUN`，保留原始输出、评审理由和失败步骤。

模型报告应绑定模型标识、执行日期、参数、角色卡和案例集校验值。首字延迟、总时延和 token 用量独立记录；费用未知时留空。人工评审可以标注不确定，不能补造输出或分数。

## 记忆方案与后续接入

目标结构为应用级会话服务加本地 SQLite：最近完整问答负责接话，摘要保留较早话题与未解决事项，结构化记忆保存有来源、有作用域和有效期的偏好或事实。角色卡单独维护。聊天窗口关闭不会自动丢弃会话，用户主动新建会话时才切换会话标识。

摘要记录已覆盖的消息范围，必要时可回查原文。记忆更正采用新状态替代旧状态；删除必须同时清除后续可检索事实与摘要中的派生信息。临时状态按有效期使用。引文和助手猜测不能升级为用户事实。

每个会话按顺序构造请求与提交回复。取消、失败和流式中间片段不作为成功助手回复入库；重试使用明确的请求标识，避免重复写入。确认保存或删除之前，应用必须完成对应事务。

早期运行副本中的模型参数适配已在 TASK-0012 保留并接入本地版本；近期会话服务也已启用。TASK-0014 在此基础上修复角色卡与历史投影，保留模型配置和语音适配器。上文 SQLite、摘要与长期记忆仍是后续目标，本案例集本身不会自动启用这些功能。

## 声音评估与执行顺序

本案例集评估朗读文本的表达和语义，不能给音色相似度或听感打分。声学比较需要固定同一组未见文本、参考声音和播放条件，再分别听基础声模、现用适配器和候选声音方案；文字得分与听音结果分别记录。

先复核角色卡和案例，再用受控输入比较文本模型。会话与记忆功能接入后执行应用集成案例。应用生命周期、跨重启恢复和删除行为通过后，再进行连续使用评估。对照题保留为评测资料；若以后用于训练，必须从评测中移除并补充独立新题。同一来源台词扩写出的变体放在同一数据分组，避免训练与评测互相泄漏。
