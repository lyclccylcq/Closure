# 可露希尔 · AI 桌面工程助手

> 「博士，你的终端好像又冒红光了哦？」
> 「别急别急，让可露希尔大人来看看——当然，维修费我们之后再谈！」

一个基于 **Java / JavaFX** 开发的 AI 桌面陪伴与编程辅助项目。

本项目以《明日方舟》中的可露希尔为角色原型。

作为血魔一族的工程师、罗德岛的工程技术专家，可露希尔将常驻在你的桌面上，观察编译器与程序的运行状态，并在项目发生爆炸之前——或者爆炸之后——提供来自罗德岛工程部的技术支援。

```text
正在连接罗德岛工程部……

工程师：可露希尔
当前状态：在线
工作内容：排查故障、分析报错、推销工程部会员
博士的项目状态：暂时还能抢救
```

## 欢迎来到罗德岛工程部

普通桌宠的工作：

* 待在桌面上；
* 播放动画；
* 偶尔回应一下鼠标点击。

可露希尔的工作：

* 待在桌面上；
* 播放动画；
* 陪博士聊天；
* 观察程序的编译与运行状态；
* 捕获突然出现的红色报错；
* 分析异常堆栈；
* 找出最有可能出问题的代码；
* 在博士准备删除整个项目之前阻止博士。

简单来说：

```text
你负责写代码。

Bug 负责突然出现。

可露希尔负责告诉你：
“这个东西到底是怎么炸的。”
```

## 角色设定

在本项目中，可露希尔将作为驻扎在博士桌面的工程技术顾问。

当开发环境处于不同状态时，她也会表现出不同的反应。

### 程序正常运行

```text
“嗯嗯，运行正常！”

“看来这次不用工程部紧急出动了。”

“做得不错嘛，博士。”
```

### 开始编译

```text
“检测到构建任务！”

“可露希尔工程部，开始工作！”
```

### 编译成功

```text
“构建成功！”

“哼哼，这点小问题当然难不倒我们工程部。”

“博士，记得给个五星好评哦！”
```

### 编译失败

```text
“警报！警报！”

“博士，你的代码好像冒烟了！”

“不要乱点重启，让我先看看日志。”
```

### 出现大量连锁报错

```text
“停——先不要被这几十条红字吓到。”

“真正的问题可能只有最上面的那一条。”

“后面的报错，大概率只是跟着一起起哄而已。”
```

### 同一个错误反复出现

```text
“博士……”

“这个问题，我刚才是不是已经讲过一次了？”

“工程部售后服务很好，但博士也要认真听哦！”
```

## 核心功能

### 桌面陪伴

可露希尔会以透明桌面角色的形式驻留在屏幕上。

当前及计划中的功能包括：

* 透明无边框角色窗口；
* 鼠标拖动；
* 双击打开聊天界面；
* 待机、说话、思考和警告动画；
* 根据程序状态切换表情与动作；
* WebM 动画支持；
* 后续考虑接入 Spine 或 Live2D。

---

### 对话系统

除了工程支援之外，可露希尔也可以作为普通的 AI 桌面陪伴助手。

计划支持：

* 文本对话；
* 对话上下文记忆；
* 大语言模型接入；
* 语音识别；
* 文本转语音；
* 角色动作与语音同步。

```text
博士：
“为什么程序又启动失败了？”

可露希尔：
“因为你把资源文件路径写成绝对路径了。”

博士：
“那为什么昨天还能运行？”

可露希尔：
“因为昨天你还没换电脑呀。”
```

---

### 开发环境监视

这是项目后续最重要的功能之一。

在获得用户授权后，可露希尔将尝试观察开发环境中的相关信息，例如：

* Maven 构建日志；
* Gradle 构建日志；
* Java 编译错误；
* 程序运行时异常；
* 单元测试失败结果；
* 终端标准输出与错误输出；
* IDE 中的错误与警告；
* GitHub Actions 等 CI 运行日志。

当程序运行失败时，系统会自动提取：

```text
异常类型
错误信息
异常堆栈
文件名称
代码行号
构建工具
退出状态码
最近修改的相关文件
```

随后由 AI 分析错误原因，并通过聊天窗口或桌面气泡向博士报告。

## 工程部报错分析

例如，当控制台出现：

```text
java.lang.NullPointerException
    at com.closure.service.ChatService.sendMessage(ChatService.java:52)
```

可露希尔可能会说：

```text
“工程部报告！”

“ChatService.java 第 52 行调用了一个可能为空的对象。”

“从当前代码来看，最可疑的是 findUser() 的返回值。”

“建议先检查用户不存在时，方法是否会返回 null。”
```

当 Maven 构建失败：

```text
[ERROR] cannot find symbol
symbol:   class MessageItemPanel
location: class ChatWindow
```

她可能会给出：

```text
“找到问题了！”

“ChatWindow 找不到 MessageItemPanel。”

“可能原因有以下几个：”

“第一，缺少 import。”

“第二，类的 package 和文件路径不一致。”

“第三，你重构时修改了类名，但是这里还在使用旧名字。”

“第四，IDE 又在装死。”
```

## 理想工作流程

传统报错处理流程：

```text
程序运行失败
    ↓
复制整段错误信息
    ↓
打开浏览器或 AI 聊天窗口
    ↓
粘贴错误
    ↓
补充项目背景
    ↓
反复说明文件结构
    ↓
得到一个不一定适用的答案
```

本项目希望实现：

```text
程序运行失败
    ↓
可露希尔发现异常
    ↓
进入工程模式
    ↓
自动提取关键报错
    ↓
定位相关文件和代码行
    ↓
读取必要的项目上下文
    ↓
分析可能原因
    ↓
主动提供解决方案
```

理想状态下，博士甚至不需要手动复制错误信息。

```text
“博士，构建失败了。”

“真正导致失败的是 ChatWindow.java 第 87 行。”

“你刚才修改了 MessageItemPanel 的构造方法，”

“但这里仍然在按照旧参数调用。”

“我整理了两种修改方案。”

“放心，这次咨询暂时不收费！”
```

## AI 编程辅助 Agent

在完成基础的日志捕获和报错分析后，可露希尔还将逐步学习更多工程技能：

* 根据异常堆栈定位相关代码；
* 读取报错位置附近的代码；
* 分析跨文件调用关系；
* 对比最近一次代码修改；
* 判断报错是否由环境配置引起；
* 生成具体的排查步骤；
* 提供代码修改建议；
* 生成可审查的代码补丁；
* 在用户确认后应用修改；
* 修改完成后重新运行验证。

默认情况下，她不会直接偷偷修改博士的代码。

```text
发现错误
    ↓
完成分析
    ↓
给出修复建议
    ↓
展示修改内容
    ↓
等待博士确认
    ↓
应用修改
    ↓
重新运行
```

毕竟工程技术的第一原则是：

```text
修不好可以继续修。

但是不能在博士不知道的情况下，
把一个 Bug 修成三个 Bug。
```

## 项目目标

这个项目并不只是：

```text
桌面角色 + 聊天窗口 + AI API
```

它真正希望实现的是：

```text
二次元桌面角色
+
开发环境感知
+
构建日志解析
+
代码上下文读取
+
大语言模型分析
+
主动式编程辅助
```

让 AI 不再只是等待博士主动提问，而是能够感知当前工作状态，在合适的时候主动出现。

当代码正常运行时，她是桌面上的陪伴角色。

当程序编译失败时，她是罗德岛工程部派来的技术专家。

当 IDE 突然爆红时——

```text
“博士，让开一点。”

“专业的事情，要交给专业的工程师。”

“……等等，这个项目怎么连我自己都编译不过？”
```
